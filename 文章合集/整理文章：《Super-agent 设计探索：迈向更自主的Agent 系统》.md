
#### 文章背景

过去一年里，以 Coding Agent 为代表的 Agent 系统调用工具解决长时序复杂问题的能力持续提升，人机协作模式中执行工作基本实现完全下放，人在协作链路中往决策与验收端偏移，且多 Agent 跨会话协作逐渐变得可行。
这些能力的提升催生了新的应用形态：个人Agent助手（Personal Agent），这些助手会直接接入用户的工作平台（如飞书、Bot API等）、项目文件夹，持续在线监听事件，自主处理事务，并且调度 Agent 集群作为同事协作。

##### 现有 Agent 设计模式的局限性

然而现有主流 Agent 设计模式在多任务和团队协作有结构性短板，当前 Agent 仍以单会话为基本单位，不同会话间彼此独立。当用户并行推进多项工作时，必须手动切换并记住各个 会话窗口的上下文，而一个人通常只能同时跟进 3 到 5 个活跃会话。在这种设计下，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

如果只在现有的本地单会话 Agent 上借助 CLI、MCP 或外部连接器做简单扩展，Agent 虽然也能接入外部消息，但仍受制于单会话同步阻塞、多任务上下文混乱、本地设备离线即停止运行等问题，需要大量人工维护。

#### Personal Agent 的基本特征

下一代的 Agent 系统应当具备以下四个基本特征：
```
1. 连续性：跨会话的记忆与主体连续性，体感上始终是同一个的agent在交接事务。
2. 高效性：用户指令即时响应无需等待，执行任务并行推进。
3. 主动性：在职责范围内主动达成“应该做”，在无事时主动待命。
4. 持久性：始终在线、在场，异常时自动处理自行归位。
```

>DSH团队认为，无论是面向个人的助手，还是面向软件开发等商业场景的 Agent，如果目标是构建一个持续在线、并发响应环境事件的系统，那么在底层就可能会采用相近的架构。同时，这一过程中面临的许多问题与传统计算机系统长期探讨的问题具有很高的相似性，因此计算机系统中的许多经典设计思想在这里同样适用。`

#### 双层架构

##### 当前 Agent 系统面临的问题：*上下文连续性 VS 多任务并发*

单会话架构：所有事件都由同一个会话处理，上下文最连续，但事件串行执行吞吐量低，且不同任务的上下文堆叠造成混乱，上下文高负载会导致模型降智。

多会话架构：每个事件另起独立会话处理，并发吞吐最高，但不同任务间相互独立缺乏协调，且需要用户同时兼顾多个会话窗口，注意力负担大。

##### Router-Worker 双层架构
为了兼顾连续性与吞吐量，DSH团队把“全局连续性”与“高并发执行”拆分为两个不同的层级：**常驻 Router 层负责统筹全局任务规划与执行调度，也是用户主要的交互入口；上下文独立的 Worker 层集群按需激活，并行执行具体任务，向上层汇报结果。**

![[Pasted image 20261105141355.png]]

>在现有设计中，Session 同时承载了技术上的上下文管理与面向用户的项目管理。将产品形态与底层 Session 解耦后，面向用户的项目管理便不再受 Session 的限制，向用户暴露怎样的交互与任务管理方式成为了一个独立的产品问题。

##### Router 层
Router 层是常驻的全局路由层，负责承接所有入口的人类交互。原则上不直接执行具体任务，甚至可以不配置Bash工具。
